`POST /api/discover/local` inspects the machine the app is running on and:

- Upserts a `servers` row keyed by hostname with hardware facts (os, cpu
  cores, memory, disk), sets `status` to `active` and `last_seen` to now,
  truncating `os_version` to 50 characters (app.py:387-396)
- Appends a `discovery_history` row whose `data` is a JSON blob of system
  facts, at most 20 processes (only those using more than 0.1% of memory),
  and listening sockets (app.py:359-410)
- Returns counts, not the stored record: `services_count` and
  `connections_count` describe what was observed, and no `services` rows
  are ever created from discovery

Any failure (e.g. psutil permission errors) returns 500 with the exception
string.

Confidence: medium. The intent (idempotent self-registration plus audit
trail) is inferred from the code and README; the thresholds (0.1%, 20, 50
chars) look arbitrary and are recorded as observed, not as requirements.
The upsert mechanism is destructive in a way that looks unintended; see
ISS-104 before treating "upsert" as the preserved meaning. No contract is
written for the discovery endpoint itself because its current behaviour
may be partly bug; CT-109 covers only the audit-trail half, that recorded
history is retrievable via GET /api/discovery/history.
