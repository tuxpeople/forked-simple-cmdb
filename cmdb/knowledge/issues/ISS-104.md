title: Rediscovery wipes server metadata and reassigns its id
status: draft
since: 2026-07-31
owner: tyson
affects: [cmdb]
---

The discovery upsert uses `INSERT OR REPLACE INTO servers` naming only the
discovered columns (app.py:387-396). In SQLite, REPLACE deletes the
conflicting row and inserts a new one, so on rediscovery of a known
hostname:

- `environment`, `location`, `owner`, `notes`, `created_at` are reset to
  defaults/NULL: hand-entered curation is destroyed by clicking "Discover
  Local" a second time
- The row gets a new `id`, so services attached to the old id are
  orphaned (ISS-102 means nothing cascades or complains)

A true upsert (`INSERT ... ON CONFLICT(hostname) DO UPDATE`) would
preserve both. The adjacent
`c.lastrowid if c.lastrowid else <select by hostname>` fallback
(app.py:398-400) is dead code, since lastrowid is always set after
REPLACE; it reads like the author expected update-in-place semantics,
which supports this being a bug rather than a choice.

Confidence: medium-high. Reasoned from documented SQLite REPLACE
semantics and the code; not reproduced against a live instance in this
mining pass.
