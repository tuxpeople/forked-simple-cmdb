The handler orders by `created_at`, but `discovery_history` has no such
column; its timestamp is `discovered_at` (app.py:745-749 vs schema at
app.py:110-118). Every request raises
`sqlite3.OperationalError: no such column: created_at` and returns a 500.

Verified by running the exact query against the repository's `cmdb.db`:
`Error: in prepare, no such column: created_at`.

Compounding it, the discover page's history table
(`templates/discover.html:195-220`) renders fields the endpoint never
returns even if fixed (`source`, `items_discovered`, `status`), so the UI
feature was never observed working; that is presumably why the bug
survived. The endpoint's *intended* 200 shape, recorded in
api.openapi.yaml, is inferred from the code around the broken line and is
itself unverified.
