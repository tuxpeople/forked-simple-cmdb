id: ISS-108
type: issue
title: Local discovery 500s whenever any process hides its memory usage
status: deprecated
since: 2026-08-06
owner: tyson
affects: [cmdb]
---

`discover_local` filtered processes with `if pinfo['memory_percent'] > 0.1`
(app.py:362-373). Inside `psutil.process_iter(attrs=[...])` psutil does not
raise for a field it cannot read: it sets that field to `None`. The
`except (psutil.NoSuchProcess, psutil.AccessDenied)` guard directly below
therefore never fires, and the comparison raised

    TypeError: '>' not supported between instances of 'NoneType' and 'float'

which the handler's broad `except Exception` turned into a 500 for the whole
endpoint. One unreadable process out of a thousand was enough to lose the
entire discovery run, and with it the only way to write a `discovery_history`
row.

Reproduced on macOS 25.3 with psutil 5.9.5: 337 of 1284 processes report
`memory_percent` as `None`, and `POST /api/discover/local` returned
`{"success": false, "error": "'>' not supported between instances of
'NoneType' and 'float'"}`. Found while writing the contract runner: CT-109
scenario 1 needs a recorded discovery run and could not get one.

Resolved 2026-08-06 in feature/contract-runner: the comparison now reads
`(pinfo['memory_percent'] or 0) > 0.1`. A process whose memory cannot be read
is simply not significant.

Note the endpoint has a second, separate limit that is not a defect and was
not changed: `psutil.net_connections(kind='inet')` requires root on macOS and
raises `AccessDenied` there, so local discovery still 500s on an unprivileged
macOS host. That failure mode is recorded as built in api.openapi.yaml ("500:
Any failure (e.g. psutil permissions)"). The contract runner reports CT-109
scenario 1 as skipped, never as passed, when the host refuses the scan; it
passes on Linux and on macOS when the socket scan is available.
